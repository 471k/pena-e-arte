**Date:** 31 July 2026 · **Reviewer:** Engineering consultation project · **Subject:**
`docs/engineering/EPIC-0001-pre-implementation-hardening.md`
**Method:** every claim below re-verified against the live source tree at commit `7e4196c` (`main`)

## 1. Headline correction — CI-level secret scanning already exists

PENA-105's acceptance criteria and PENA-107's acceptance criteria both propose adding a
"secret-scanning pre-commit hook and CI step (`gitleaks` or `truffleHog`)" as net-new work. This is
half wrong: **the CI step already exists.**

`.github/workflows/ci.yml`, `guardrails` job (lines 214–235), runs `gitleaks/gitleaks-action@v2` on
every PR, with a code comment noting it was verified against a real PR run (the
`pull-requests: read` permission fix for the gitleaks-action's commit-listing call). This is present
at commit `7e4196c` itself — `git diff 7e4196c -- .github/workflows/ci.yml` returns no changes, so
this isn't drift since the epic was written, it was already there when the epic's own "verified
against commit 7e4196c" pass should have caught it.

It gets stronger: `docs/claude/architecture.md` — the epic's own #1-listed source of truth for
cross-cutting architecture — documents this twice. Its CI section (line 2891) describes the
`guardrails` job's gitleaks step directly, and its Decisions Log (line 1525) records that **native
GitHub secret scanning + push protection were also enabled at the platform level on 2026-07-26**,
five days before this epic — "complementary to the in-CI gitleaks step (gitleaks runs post-push in
`guardrails`; push protection blocks the `git push` itself before the commit lands)." So there are
already two layers (push protection, then CI) in front of the one this epic proposes adding a third
of.

**What's actually still missing:** a **local pre-commit hook**. Nothing today stops a secret from
being `git add`-ed and committed locally before push protection or CI ever see it — a developer who
commits then amends/resets before pushing never triggers either existing gate. That's real, novel
work. Everything else in PENA-105's and PENA-107's secret-scanning ACs should be reworded from "add"
to "confirm existing gitleaks-in-CI and push-protection already satisfy this; add only the
pre-commit hook (e.g. a `gitleaks protect --staged` pre-commit hook via `husky`/`lefthook` or a
plain `.git/hooks/pre-commit` script, document the install step in whatever contributing guide
PENA-107 starts)."

**Effort impact:** shaves real time off both PENA-105 (drop the CI-step half of that AC) and
PENA-107 ("wired in here if not already done" — it's already done; PENA-107's job becomes writing
the pre-commit hook, if that's judged to belong there instead of PENA-105, plus the Help-sync CI
check and architecture-test CI job, which remain genuinely missing — confirmed no `helpContent`,
`architecture`, or `NetArchTest` references anywhere under `.github/`).

## 2. Second correction — PENA-105's secrets list is incomplete in a way that matters today

PENA-105's problem statement claims all seven listed secrets (`Jwt:SecretKey`, `Stripe:SecretKey`,
`Twilio:AuthToken`, `Resend:ApiKey`, `CloudflareR2:SecretAccessKey`, `Instagram:AppSecret`,
`Instagram:TokenEncryptionKey`) are "populated at runtime via environment variable substitution in
`docker-compose.yml`." Checked the `api` service's `environment:` block directly (lines 146–169):
only **four** of the seven are actually wired — `Jwt__SecretKey`, `Stripe__SecretKey` (+ three more
Stripe keys), `CloudflareR2__*` (5 keys), and `Resend__ApiKey`. **`Twilio__AuthToken`,
`Instagram__AppSecret`, and `Instagram__TokenEncryptionKey` have no corresponding lines in
`docker-compose.yml` at all** — they exist as empty-string placeholders in `appsettings.json` and
nowhere else.

This isn't cosmetic. Both integrations are real and active: `NotificationService.cs` uses Twilio for
SMS, and `InstagramService.cs` + `InstagramSyncJob.cs` run a scheduled Instagram sync. In a
docker-composed deployment, both would run today with permanently empty credentials no matter what's
set in `.env` — a concrete, shippable-today bug, independent of the Vault-vs-env-vars architecture
question PENA-105 is actually about.

**Recommendation:** either fold a two-line `docker-compose.yml` fix (`Twilio__AuthToken:
${TWILIO_AUTH_TOKEN:-}`, `Instagram__AppSecret: ${INSTAGRAM_APP_SECRET:-}`,
`Instagram__TokenEncryptionKey: ${INSTAGRAM_TOKEN_ENCRYPTION_KEY:-}`) into PENA-105 explicitly as its
own numbered AC item, or — better, since it's unrelated to the Vault migration and blocks nothing —
spin it out as its own one-line ticket so it isn't waiting on PENA-105's 3–5 day estimate to land.
Flag this choice to the founder per the same judgment call PENA-105 already makes about Vault vs.
Infisical/Doppler.

## 4. Structural gap — Help-sync verdicts are inconsistent across tickets

This project's own non-negotiable rule (and CLAUDE.md rule 7) requires every deliverable to carry an
**explicit** Help-sync verdict — including an explicit "no update needed, because X" when true, never
silence. The epic itself states this as Definition of Done item 4 ("A ticket that changes
user-facing behavior without a Help diff fails review on that basis alone, no exceptions") and gives
PENA-103 and PENA-106 dedicated `### Help sync (DoD item 4)` sections with concrete file/article
references. The other six tickets don't follow that pattern consistently:

| Ticket | Explicit Help-sync section? | Verdict needed |
|---|---|---|
| PENA-100 | **No** | Should have one. New `SiteFooter` renders on every public route with new links — user-visible. `helpContent.ts` likely has no article for a footer today (nothing to update), but the ticket should say so explicitly rather than omit the question. |
| PENA-101 | **No** | Defensible as N/A (bug fix restoring existing links, no new behavior) — but say so explicitly rather than omit it, per the rule's own "even then, say so explicitly" clause. |
| PENA-102 | Partial — mentioned only inline in the **Testing** section, not as its own DoD subsection | Should be promoted to a full subsection: these are first-touch public pages, onboarding-tour relevance for `ClientRegisterPage`/`RegisterStudioPage` flows should be checked explicitly, not folded into a testing aside. |
| PENA-103 | **Yes** — full section, concrete | No action needed. |
| PENA-104 | **No** | The right-to-erasure request path, if it ships a self-service UI surface (the ticket leaves this open — "flag it rather than silently absorbing new scope"), needs a Help-sync verdict once that's resolved. As written today (backend job + audit trail only), N/A is defensible — but again, say so. |
| PENA-105 | **No** | Legitimately N/A — infra/secrets plumbing, zero user-visible surface. This is exactly the one exemption case the rule allows, but the epic should state it explicitly rather than let it read as an oversight. |
| PENA-106 | **Yes** — full section, concrete (payment Help copy going provider-neutral) | No action needed. |
| PENA-107 | **No** | Legitimately N/A — DevOps/CI only. Same as PENA-105, state it explicitly. |

None of this changes what ships. It's bookkeeping the epic's own Definition of Done already commits
to, and per this project's standing instructions, an unstated "no Help change needed" is treated as
a gap, not a pass. Cheap fix: add a one-line Help-sync verdict line to PENA-100, 101, 102, 104, 105,
and 107 before this goes to an implementing session, so DoD item 4 is actually checkable per ticket
instead of assumed.

## 6. Industry-benchmark check

This project's standing rule requires every deliverable to be checked against the vertical
booking-SaaS competitor set (Vagaro, Fresha, Boulevard, etc.) and, separately, general B2B
platform-admin standards. **This epic correctly does not force that lens onto itself, and that's the
right call, not a silent omission worth flagging** — none of these eight tickets are user-facing
competitive features; they're legal/compliance/infra hardening. Each ticket's own "Industry standard"
section instead cites the actually-relevant standard for its subject: GDPR Art. 5/7/9/17, Law
124/2024, e-Commerce Directive Art. 5, OWASP ASVS V6, CWE-798, PCI DSS SAQ-A scope discipline,
NIST SP 800-53 SI-12, and the ArchUnit/fitness-function pattern for PENA-106's architecture test.
That's the correct benchmark set for this category of work, explicitly named per ticket rather than
assumed — no gap here.

## Summary of required changes before this goes to an implementing session

1. **PENA-105**: strike or reword the CI-step half of the gitleaks/truffleHog AC — it's already live
   in `guardrails` (`ci.yml`) and already documented in `architecture.md`'s Decisions Log. Keep the
   pre-commit-hook half; that's genuinely missing.
2. **PENA-107**: same correction — the secret-scanning line item is "already done as part of
   [PENA-105]" in the epic's own words, and now we can say so with certainty rather than hedge it.
3. **PENA-105**: add `Twilio__AuthToken`, `Instagram__AppSecret`, `Instagram__TokenEncryptionKey` to
   the problem statement and either fold a `docker-compose.yml` fix into the AC list or spin it out
   as its own fast-follow ticket — both integrations are live and currently running with credentials
   that can never be populated in a docker-composed deployment.
4. **PENA-100**: correct the "no footer component exists" claim to specify "no site-wide legal
   footer" and note `AuthShellFooter.tsx`'s actual (different) purpose.
5. **PENA-102**: correct the `CookieConsentBanner.tsx` AC — it isn't a "verify the link" task, the
   banner has no policy link and no consent categories today (single accept-all button, blanket
   copy). Reframe as "add a `/privacy` link" and flag, separately, whether an accept-all-only banner
   with no category distinction is adequate once any non-essential (analytics/marketing) cookie is
   ever added — it currently isn't distinguishing essential from non-essential in a way that would
   hold up if that changes.
6. **PENA-106**: correct "12 methods" to 10 on `IStripeBillingService.cs` (cosmetic only).
7. **PENA-100, 101, 102, 104, 105, 107**: add an explicit one-line Help-sync verdict to each (either
   the concrete update or an explicit "N/A — no user-visible surface, because X"), matching the
   standard PENA-103 and PENA-106 already set.

None of these require re-scoping any ticket's engineering estimate materially except PENA-105, which
should get *smaller* once the redundant CI-step work is removed and *slightly larger* once the
Twilio/Instagram docker-compose fix is folded in — those two roughly cancel out. The epic remains
safe to route to an overnight session once the above are patched in.
